## متى تُستخدم

- يريد المستخدم إعطاء مهمة لوكيل متصفح مستضاف (Browser Use Cloud Agent) أو تشغيل متصفح سحابي والاتصال به عبر CDP من كود Playwright/Puppeteer.
- يطلب المستخدم كتابة أو مراجعة كود تكامل مع Browser Use، أو تشخيص أخطاء 409/429/فشل تشغيل، أو فهم الحصص والفوترة.

## التعليمات

1. **V4 للتكاملات الجديدة:** استخدم API V4 دائمًا مع الاستيراد الصريح `from browser_use_sdk.v4 import BrowserUse` (في TypeScript: `from "browser-use-sdk/v4"`). اجعل أمثلة V3 موثّقة بالإصدار صراحةً. مكتبة open-source وSDK المستضاف لهما واجهتان مختلفتان — لا تخلط بينهما.
2. **المصادقة:** المفتاح يُرسل في الترويسة `X-Browser-Use-API-Key` **بدون** بادئة `Bearer`. اقرأه من البيئة (`BROWSER_USE_API_KEY`) ولا تطلبه أو تضعه في الكود أو المحادثة أبدًا.
3. **إيقاف المتصفح إلزامي:** انقطاع CDP أو اكتمال التشغيل أو انتهاء مهلة الانتظار لدى العميل **لا يوقف** المتصفح السحابي. أوقف المتصفحات غير الضرورية صراحةً داخل كتلة `finally`: `client.browsers.stop(session.id)` أو `PATCH /api/v4/browsers/{id}` مع `{"action":"stop"}` — حتى عند فشل الاتصال أو التنقل.
4. **حدود معدل الطلبات بنوافذ 5 ثوانٍ:** `X-RateLimit-Limit=125` تعني 125 طلبًا لكل نافذة زمنية (≈25 RPS) وليس 125 RPS. التزم بـ `Retry-After` المُعاد. استخدم عددًا محدودًا من العمال (bounded workers)، وزعّم الاستعلامات (stagger polls)، واستنزف صفحات الأحداث `hasMore` بعد الحالة النهائية. جلسة V4 مشغولة تُعيد 409 وطابورها 20 رسالة فقط وليس طابور دفعات على مستوى المشروع.
5. **التزامن شيء ومعدل الطلبات شيء آخر:** اقرأ سعة التزامن ورصيد الحساب من `GET /api/v2/billing/account` (`concurrentSessionLimit`, `activeSessionCount`, `projectId`). المفاتيح في المشروع الواحد تتشارك السعة والأرصدة.
6. **قيم التفكير لكل نموذج:** نموذج `GPT-6 Astra` يقبل `low`, `medium`, `high`, `xhigh` (الافتراضي), `max` — القيمتان `none` و`minimal` غير صالحتين. لا تخترع حقولًا غير موجودة في الـ SDK؛ ارجع لمخطط REST العام عندما تتأخر أنواع الـ SDK.
7. **التفريق بين المفاهيم:** مهلة العميل ≠ مهلة التشغيل على الخادم ≠ اكتمال المهمة. قبل إعادة تشغيل مكررة، تأكد من حالة التشغيل الفعلي وطبّق أي أثر خارجي (طلبات، نماذج) أرسله التشغيل السابق. `is_done` تعني تنفيذ أمر إنهاء صريح فقط، و`is_successful` رأي الوكيل نفسه — تحقق من الأفعال الخارجية المهمة بشكل مستقل.
8. **التفاصيل الكاملة** في المرجع: `references/browser_use_v4_guide.md` (القواعد المختصرة)، والنسخة الكاملة في `docs/browser_use_v4.md` بمستوى المستودع.

## قائمة التحقق قبل الرد النهائي

- [ ] الكود يستورد من `browser-use-sdk/v4` صراحةً (وليس استيرادًا افتراضيًا قديمًا).
- [ ] الترويسة `X-Browser-Use-API-Key` بدون `Bearer`، والمفتاح من متغير بيئة.
- [ ] يوجد `finally` يوقف كل متصفح بدأه الكود (`browsers.stop` أو `PATCH .../{"action":"stop"}`).
- [ ] الاستعلام/الانتظار يحترم `Retry-After` و`hasMore`، ولا يضرب الـ API بحلقة ضيقة.
- [ ] لا توصية باشتراك جديد لتفعيل proxies أو BYOK (السحابة pay-as-you-go)، ولا ذكر لـ Box/Bux (موقوفان).
- [ ] النتائج الخارجية المهمة مُتحقق منها بمصدر مستقل، لا بالاعتماد على `is_successful` وحدها.

## حدود المهارة

- هذه المهارة **توثيق وتأليف كود فقط** — لا تنفّذ التكامل بنفسها. لتشغيل الكود فعليًا حمّل مهارة `code_execution` (بموافقة مستقلة) ولا تطلب موافقة واحدة تخدم الاثنين.
- لا تُرسل أي مفتاح API إلى مواقع أو سجلات، ولا تضعه في ملف داخل `workspace/` قابلًا للقراءة من مهارات أخرى.
- لا تتصفح مواقع حساسة أو بنكية عبر الوكيل السحابي دون إذن صريح من المستخدم، وتذكّر أن IP البروكسي غير مضمون التفرد أو المدينة.
- إذا فشل الطلب: راجع https://docs.browser-use.com/cloud/guides/troubleshooting.md وافحص الخطأ الكامل والمشروع قبل اقتراح إعادة المحاولة أو إضافة رصيد.
